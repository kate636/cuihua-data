### 2.1 EUC 兜底链不完整 → 30.3% 利润为虚增 🔴

**严重程度**: 致命 — 总利润被高估 ~26,945 元（最新代码，含加工关系 API 优先修复）

**现象** (31天全月):
- 1,240 个 SKU 的 `effective_unit_cost = 0`（占比 ~5%）
- 5 月全月虚增利润 26,945 元，占总利润 30.3%
- 旧代码此比例为 52.3%（46,799 元），加工关系修复后下降 22pp
- 受影响的品类：基础食品类、休闲食品类、水饮类、烘焙类等（无进货记录但有销售的 SKU）

**根因**:
[skt_cost.py](fmetl/calculated/sku_cost.py) 的 EUC 兜底链缺少文档中声称的两层回退：

| 层级 | 文档描述 | 代码实现 |
|:---:|------|:---:|
| 1 | `V10_WEIGHTED_AVG` (cost_qty > 0) | ✅ 已实现 |
| 2 | `V10_INHERITED_EUC` (ffill 继承前日) | ✅ 已实现 |
| 3 | `V10_AVG_INBOUND_FALLBACK` | ✅ 已实现 |
| 4 | `V10_COST_PRICE_FALLBACK` | ❌ **未实现** |
| 5 | `V10_RETAIL_ESTIMATED_FALLBACK` (current_price × 0.40) | ❌ **未实现** |

代码第 11 行注释 "不用 cost_price" 与文档矛盾。`cost_price` 被加载但仅用于 compose 兜底，不用于 EUC 兜底。`current_price` 甚至未被加载到 sku_cost.py。

**关键数据**：在 861 个 EUC=0 的 SKU 中：
- 841 个（97.7%）有 `current_price > 0` → 添加 `current_price × 0.40` 兜底即可覆盖
- 仅 1 个有 `cost_price > 0` → cost_price 兜底覆盖率极低
- 0 个有 `avg_inbound_price > 0` → 第三层兜底完全无效

**修复建议**:
1. 在 `sku_cost.py` 加载 `current_price`（从 `t_atomic_wide`）
2. 在 ffill 之后、`avg_inbound_price` 兜底之后，增加：
   - 第 4 层：`cost_price` 兜底（`effective_unit_cost = cost_price`），标记 `V10_COST_PRICE_FALLBACK`
   - 第 5 层：`current_price × 0.40` 兜底，标记 `V10_RETAIL_ESTIMATED_FALLBACK`
3. 运行 ETL 并验证：EUC=0 的 SKU 数量和利润贡献应大幅下降

**预估修复后效果**:
- 虚增利润从 26,945 降至 ~15,000（减少 ~12,000）
- 总利润从 88,948 降至 ~77,000（-13%）
- 剩余 EUC=0 利润仍需通过加工关系/成本价补充来消除

### 2.2 sku_cost.py 与 stock.py 跨日 init_stock 查找不一致 🔴

**严重程度**: 致命 — 两个模块对同一 SKU 可能使用不同的 init_stock

**文件**: [sku_cost.py:90-102](fmetl/calculated/sku_cost.py#L90) vs [stock.py:164-182](fmetl/calculated/stock.py#L164)

**根因**: 两个模块都从 `t_calc_stock` 取前日 `end_stock` 作为当天 `init_stock`，但 day_clear 匹配方式不同：
- `sku_cost.py`: **不过滤 day_clear** — `MAX(business_date) WHERE business_date < 当天`，可能匹配到 day_clear='0' 或 '1' 的任意行
- `stock.py`: **按 day_clear 分组** — `GROUP BY store_id, article_id, day_clear`

对于同时存在 day_clear='0' 和 '1' 两行的 SKU（日清覆盖的 SKU），sku_cost.py 的 init_stock（用于 EUC 计算）可能与 stock.py 的 init_stock（用于库存方程）不一致。

**修复**: sku_cost.py 的 prev_df 查询也应按 `day_clear` 分组匹配。

### 2.3 BOM 父品库存转移后产生负毛利 🔴

**严重程度**: 致命 — CLAUDE.md 声称"父品 profit=0"但代码无法保证

**文件**: [stock.py:423-430](fmetl/calculated/stock.py#L423) + [profit.py:94-100](fmetl/calculated/profit.py#L94)

**根因**: 库存转移将父品 `end_stock` 清零并记录 `stock_transfer_out`，但 profit.py 的公式不包含 `stock_transfer_out`：
```python
profit = sale - receive - bom_in + bom_out - compose_in + compose_out + end - init
```
如果父品 `init_stock > 0`（首次处理时来自源表值），转移后 `end=0`，则 `profit = 0 - init = -init_stock`，产生负毛利。

**触发条件**: BOM 父品同时满足：有源表 init_stock、sale_qty=0、bom_out>0、end>0（触发转移）。

**修复**: profit.py 应识别 `stock_transfer_out > 0` 的父品行，在公式中额外减去 `stock_transfer_out_amt`。

### 3.7 QDM 周期性库存核销与牛羊类负毛利 🔴

**严重程度**: 高 — QDM 在特定日期出现 FM 无法匹配的巨额利润波动

**5/15-5/16 QDM 极端波动**:
- **5/15 QDM -3,354 vs FM +3,747**: QDM 对非易腐品（农夫山泉 550ml -1,860、洁柔纸巾 -1,810 等）进行库存核销，这些 SKU 当天无销售无进货，纯损失。FM 不受影响（库存方程不产生此类核销）。
- **5/16 QDM +6,788 vs FM -380**: QDM 回补（核销后库存成本归零，后续销售 100% 毛利），FM 则因前日库存消耗而正常偏低。
- **净效应**: 5/15+5/16 QDM 合计 +3,434 vs FM 合计 +3,367，两日合并后差异仅 +67（+2.0%）。说明 QDM 的核销-回补是会计期间的计时差异，不是真正的盈亏差异。

**牛羊类系统性 QDM 负毛利**:
- QDM 牛羊类 5 月合计 -1,414 元，15/31 天为亏损
- FM 牛羊类 5 月合计 +1,114 元，差异 +2,528
- **根因**: QDM 的成本确认更接近收付实现制（receive 直接扣减利润），FM 通过 EUC 加权平均将进货成本平滑分摊到销售周期
- **FM 更符合会计匹配原则**: 成本应在销售时确认，而非进货时

**建议**: 对于 5/15 类 QDM 单日极端值，评估时使用 2-3 日滚动窗口。单日对比在 QDM 核销日/回补日会产生虚假的大偏差。

### 3.8 蛋类 -34.9% 系统性偏差 🔴

**严重程度**: 高 — FM 低估蛋类利润 1,202 元（31天）

**现象**: 蛋类 FM 毛利 2,246 vs QDM 3,448，FM 系统性偏低。销售额完全一致（23,246），说明差异全部来自成本侧。

**可能原因**:
- 蛋类的日清处理与 QDM 不一致（QDM 可能不将蛋类视为日清）
- 蛋类 EUC 计算中的 compose 成本偏高
- 蛋类的 dim_day_clear 覆盖范围与 QDM 实际处理有偏差

**修复建议**: 逐 SKU 对比蛋类成本差异，确认日清覆盖是否正确。

## 四、设计层面的讨论 (P2)

### 4.1 盘盈（负损耗）处理

FM 的库存方程在"正常"分支不产生盘盈（`unknow_lost = 0`），而 QDM 可以有负损耗（盘盈）。差异约 -150/天。

**是否接受**: 可接受。FM 偏保守（利润偏低），QDM 偏激进（盘盈直接增加利润）。这是结构性差异，短期无法完全对齐。但建议：
- 扩大 `atomic_inventory_detail` 的数据使用范围（不仅是人工盘点，系统快照的实盘数也可触发盘盈）
- 代码 L346 已处理 "act_qty > eq" 的情况，但依赖该表有数据——需确认覆盖率

### 4.2 40% 成本率假设

`current_price × 0.40` 假设零售毛利率 60%。不同品类实际成本率差异大（现烤面包 vs 饮料 vs 零食）。

**建议**: 在品类维度上差异化成本率（如烘焙品 35%、标品 65%、水果 45%），而非一刀切 40%。

### 4.3 BOM 不对称（1,420.86，排除 transfer 后 0.00）

全局 `SUM(bom_in_amt) - SUM(bom_out_amt) = 1,420.86`（31天）。排除 `stock_transfer_in_amt` 后为 **0.00**。**根因已确认**：`t_calc_bom_alloc` 本身完全对称，差异来自库存转移逻辑在 [stock.py:449](fmetl/calculated/stock.py#L449) 增加了子品 `bom_in_amt` 但不增加父品 `bom_out_amt`。这是**设计行为**（防止 profit 公式中库存转移虚增子品利润）。

**建议**: 在验证 SQL 和文档中注明 BOM 对称检查需要排除 `stock_transfer_in` 的影响。

### 4.4 跨日依赖链的稳定性

`MAX(business_date) < 当天` 的设计优于 timedelta -1，自动跳过非连续日期。当前实现正确。

但需注意：修复 BOM 等影响库存的模块后，跨日链需要运行两遍才能完全更新（第一遍用旧库存链的 init_stock，第二遍用新库存链的 init_stock）。
