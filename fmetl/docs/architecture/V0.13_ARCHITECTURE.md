# fmetl v0.13 架构与当前完成度

## 架构判断

旧 v0.11 的三层命名是清楚的，但实现边界并不完全清楚：`receive_sale`、BOM 关系、加工关系、
单位换算和 matnr 曾在不同模块中互相无其他依据时采用，部分金额也会在多个阶段重算。它适合保留作历史
验证依据，不适合继续增量修补。

v0.13 采用“来源合同 → 关系判定 → 事实计划 → 每日状态 → 报告调整 → 输出”的单向过程。
每个数字只在一个层级取得权威语义，无法判定的关系进入未处理记录表，不以 fallback 悄悄进入利润。

```text
v1.5 sync_strategy_fm.sh (28 tables, A3XV)
                  │
                  ▼
mirror contracts / atomic observations
                  │
                  ├──── order events ──── order visits / weekly new-old
                  │
                  ▼
relation resolution
  ├─ DISASSEMBLY_BOM    猪肉一拆多
  ├─ PACK_CONVERT       蔬菜/水果一对一包装换码
  ├─ RECIPE_COMPOSE     多原料到成品
  ├─ PROCUREMENT_ALIAS  订货码到验收码
  └─ QUARANTINED        冲突关系，不计入每日库存和成本
                  │
                  ▼
DailyCostStock (date serial, SKU state)
                  │
                  ▼
accounting profit/loss ── v1.5 CCJ/SSLS reporting adjustment
                  │
                  ▼
FM outputs + validation + explicit publish
```

## 不可跨越的边界

| 层 | 负责 | 不负责 |
|---|---|---|
| mirror | 无损抽取源数据副本字段、检查完整性 | 重算利润、猜测去重键 |
| relations | 给关系依据定唯一类型 | 因关系存在而产生数量流 |
| facts | 保存当日实际事件和明确计划 | 给无事件的 SKU 造转换量 |
| DailyCostStock | 每日一次性计算成本、库存、内部金额流 | 分类和运营 KPI |
| special wastage | 同时保留库存和毛利基础计算值，以及 v1.5 展示调整值 | 用展示调整覆盖基础计算值 |
| outputs | 汇总已经计算完成的基础指标 | 在输出层重新计算成本 |

## 当前实现到哪里

已实现并测试：28 张源数据副本 allowlist（其中 18 张已有字段抽取合同）、API 分片防漏、
A3XV/有效营业日/品类规则、订单技术键、客次与周内新老客、关系解析、包装/BOM/加工的
安全字段合同、销售、退回、已知损耗、盘点和日清的商品每日记录整理、单日库存状态计算、利润接口、
特殊损耗调整。

尚未实现：全部 28 张表的字段合同、整段日期抽取事务、关系快照写入数据库、跨日重放器、全部输出表、
内部金额 posting、月度 QDM 对比和生产 publish。因此当前版本是可验证的重构基础，
不是可替换生产的完整版本。

## 关键数据决定

- 订单金额/数量原样保留源符号；退款、退货不再乘负一。
- 客数是完成订单客次，不是用户人数。
- 有效营业日是 A3XV 且 `bf19_sale_amt >= 500`。
- 分类规则精确跟随 v1.5 的 CASE 顺序与 119 SKU 清单。
- 猪肉 `DISASSEMBLY_BOM` 可一拆多；蔬菜包装必须是 `PACK_CONVERT` 且有实际事件。
- 优先使用 `compose` 的实际数量；配方只补缺失的一侧，不根据销售量自动生成加工记录。
- matnr 只作身份/成本对照，不自行产生库存流。
