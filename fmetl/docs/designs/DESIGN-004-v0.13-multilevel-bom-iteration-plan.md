# DESIGN-004：v0.13 多级 BOM、SPU 与库存损耗迭代计划

> 状态：设计审查 / 待业务确认后实施  
> 版本边界：仍为 **fmetl v0.13**，不新建 v0.14 目录  
> 日期：2026-07-16  
> 门店：广州滨江宏岸店（A3XV）  
> 验证期：2026-07-08 至 2026-07-14  
> 输出查看明细：日 × 门店 / 大分类 / 中分类 / 小分类 / SPU；业务报告不查看明细 SKU

## 1. 结论先行

本轮不应推翻 v0.13 的日加权成本账本和统一日内 DAG。需要重做的是其上游的
**关系决策与数量计划层**。

当前 v0.13 已具备以下正确基础：

- 当日期初数量和金额精确等于上一日期末；验证周内每天的前后差为 0；
- 同一天 BOM、包装和加工可以在统一 DAG 中按拓扑顺序定价；
- 每个内部事件的转出金额等于转入金额；
- 每个 SKU 当天只进行一次加权成本和库存状态转换；
- 有效的系统 0 库存快照可以作为实盘结果，符合已核实的 21279829 案例；
- 物料码和 SPU 目前只用于识别商品和关系候选，不会直接合并不同 SKU 的库存数量和金额。

当前主要问题是：

1. 可售表虽已建模，但 BOM 关系判断流程尚未读取它；
2. 只有猪肉的一拆多关系可以进入正式 BOM，牛羊和非猪牛羊规则尚未实现；
3. 没有公司规则所要求的 SPU 路由和目标 SKU 选择器；
4. 没有从验收商品递归展开到叶子商品；
5. 加工成品不会继续沿 BOM/SPU 过程落到叶子商品；
6. 盘点没有检查同一 BOM/SPU 组件中主子商品同时盘点的冲突；
7. 当前按层级输出只正式支持门店、大、中、小分类，SPU 仍是对比脚本临时聚合。

因此，前一轮发现的库存量和未知损耗差异，不能简单归因于库存价格。关系数量没有正确
落到最终可售叶子，会先形成数量平衡差，再由加权成本把平衡差变成未知损耗金额。

## 3. 公司多级 BOM 规则的可执行化

### 3.1 关系必须分成四个概念

| 概念 | 作用 | 是否产生库存流 |
|---|---|---|
| BOM | 验收商品到组成/拆分商品 | 是 |
| SPU | 同款商品不同销售规格间选择与换算 | 只有符合公司决策时才是 |
| 加工配方 | 多原料到一个加工成品 | 有实际加工或批准补侧时是 |
| 物料码/名称相似 | 候选发现与人工核实 | 默认否 |

不能因为两个 SKU 的 `spu_id`、`matnr` 或名称相似，就直接合并库存和成本。关系必须带：

- 门店；
- 有效日期或快照；
- 来源和目标；
- 方向；
- 数量换算；
- 决策规则；
- 依据来源；
- 是否允许正式转换记录。

### 3.2 公司决策树

对每个 `门店 + 日期 + 验收商品`：

1. 没有 BOM：库存留在验收商品，除非存在经批准的独立 SPU/包装转换事件；
2. 猪、牛、羊且有 BOM：强制全部 BOM-10，继续递归到叶子；
3. 其他商品：统计当天所有直接子商品的可售数量；
4. 子商品全部不可售：进入 SPU 路由；
5. 只有一个子商品可售且主商品也可售：不拆，库存留主商品；
6. 多个子商品可售：全部 BOM-10，继续递归到叶子；
7. SPU 路由下：
   - 1 个可售 SKU：全部给该 SKU；
   - 多个可售 SKU：按转换比例升序，再按 SKU 编码升序取唯一目标；
   - 0 个可售 SKU：库存留验收商品。

公司材料没有定义“只有一个子商品可售，但主商品不可售”的分支。验证周实际出现
**32 个父品日**，实施前必须确认，见第 11 节。

### 3.3 叶子定义

叶子不能简单定义为“当前没有子边的 SKU”，而应定义为：

> 在当天关系快照和当天可售决策下，从当前节点继续执行公司决策树后，不再产生正式下游
> 库存流的节点。

所以同一商品可能在不同日期因可售状态变化而成为叶子或中间节点。

## 4. 当前 v0.13 与公司规则的差异

| 规则 | 当前 v0.13 | 公司逻辑 | 结论 |
|---|---|---|---|
| 可售来源 | 已有标准化模块，但验证流程未读取 | 每天按门店商品可售状态判断 | 明确缺失 |
| 猪肉 | 猪肉且父品 fanout≥2 才允许 BOM | 猪类有 BOM 就强制拆 | 单子品猪 BOM 也可能漏掉 |
| 牛羊 | 不满足猪肉过滤，通常不进 BOM | 有 BOM 强制 BOM-10 | 明确缺失 |
| 非猪牛羊 | 一对一换算有事件时作为 PACK | 按 0/1/多可售子品决策 | 明确缺失 |
| BOM-10/20 | `bom_type/split_mode/sp_level` 未参与决策 | 业务规则明确区分并重定业务关注点 | 明确缺失 |
| SPU 路由 | 没有已确认关系和目标选择器 | 0/1/N 可售并按比例、编码排序 | 明确缺失 |
| 多级过程 | 账本支持 DAG，但计划器只消费单跳 `receive_sale` | 验收到最终叶子 | 明确缺失 |
| 加工后路由 | 成品落在 finished SKU | 有过程则继续落叶子 | 明确缺失 |
| 物料码 | `NO_POSTING`，只作身份快照 | 不能单独证明库存换码 | 当前方向正确 |
| 盘点快照 | 所有合法非负 actual 都是正式余额 | 手工和系统盘点都有效 | 基本一致 |
| 主子同时盘点 | 无组件冲突检查 | 会产生双向转换和负库存风险 | 明确缺失 |
| 加工库存检查 | 日粒度总池不得透支 | 加工时原料必须有库存 | 只能证明日粒度，不能证明时点 |

### 4.1 代码层依据

- `relations/resolver.py` 仅在猪肉且一父多子时允许 BOM；
- `validation/run_shadow_week.py` 的关系候选只来自当日 `receive_sale` 跨码边和加工配方；
- BOM 静态图本身不会从验收商品递归生成候选；
- `master_data/saleability.py` 已实现每日可售状态整理，但主要计算流程尚未调用；
- `relations/matnr.py` 明确标为 `NO_POSTING`；
- `facts/processing_plan.py` 只把加工成品记到 finished SKU；
- `calculations/ledger.py` 已具备统一 DAG 的拓扑执行能力，可以保留；
- `facts/sku_day.py` 把所有合法非负库存快照作为正式余额，并保留人工/系统来源依据。

## 5. 源数据副本层量化结果

### 5.1 多级 BOM 确实存在

七天完整 BOM 图每天约有：

- 427–434 个父节点；
- 434–441 个一级子节点；
- 61–66 个“子节点同时又是下一层父节点”的中间节点。

按验证周实际有验收的根节点计算，每天均有：

- 3 个活跃中间节点；
- 8 个二级子节点。

因此当前单跳计划器一定会漏掉真实的第二层路由。底层账本无需重写，但关系计划必须递归。

### 5.2 当前已确认关系覆盖

验证周当前关系解析结果：

| 关系类型 | 行数 |
|---|---:|
| DISASSEMBLY_BOM | 483 |
| PACK_CONVERT | 18 |
| RECIPE_COMPOSE | 483 |
| SELF_RECEIVE | 189 |
| UNRESOLVED | 47 |

此外：

- 10 个内部事件因来源没有成本种子被不计入正式计算；
- 22 个加工 relation-day 因实际加工量与配方不一致被不计入正式计算；
- 189 个 `raw=finished` 配方属于身份/标签元数据，继续只审计、不产生库存流。

### 5.3 验证周无法覆盖公司所有分支

按有实际验收的父品日：

- 猪肉强制 BOM：33 个父品日；
- “唯一子品可售且主品可售，库存留主品”：22 个父品日；
- “唯一子品可售但主品不可售”：32 个父品日，规则未定义；
- 验证周没有实际符合“所有子品不可售→SPU”以及“非猪牛羊多个子品可售→BOM”的验收事件。

所以 SPU 和非猪牛羊多子 BOM 不能只靠这一周真实数据验收，必须补历史样本或由已核实案例
建立固定测试夹具。

## 6. 目标架构

```text
权威源数据副本层
  ├─ 验收/进货事实
  ├─ 日级可订可售
  ├─ 商品/SPU/物料码
  ├─ BOM 边和单位换算
  ├─ 实际库存转换明细（待确认能否新增）
  ├─ 盘点明细
  └─ 实际加工 + Foodmart 配方快照
          ↓
关系依据快照
          ↓
company_bom_policy：逐父品日输出唯一决策
          ↓
multilevel_leaf_plan：递归到叶子，环/冲突不计入正式计算
          ↓
统一 BOM / SPU / PACK / COMPOSE 日内 DAG
          ↓
现有 DailyCostStock 加权库存处理规则
          ↓
门店 / 大 / 中 / 小 / SPU 分层影响与正式输出
```

关系层必须输出“为什么这样拆”，而不仅是最终数量：

```text

current_article_id / target_article_id
relation_type / path_depth
parent_saleable / saleable_child_count
decision_rule / decision_evidence
conversion_ratio / ratio_source
is_leaf / formal_flow_allowed / quarantine_reason
relation_snapshot_id
```

## 7. 分块实施计划

原则：每个块单独完成测试和分层对比，通过后才进入下一块。每块均保留运行日志、关系快照、
输入输出行数、平衡平衡差和差异 Top 路径。

### Block 0：固定修改前结果并列出验收项

不改库存逻辑，只固化当前周结果：

- 固化当前源清单 checksum、关系快照 checksum 和 Git SHA；
- 保存当前门店/大中小/SPU 对比结果；
- 固化每日前一天期末库存转为当天期初库存、内部数量净流、未知损耗数量和金额；
- 将 SPU 缺失的 2026-07-09 v1.5 分区标记为非阻塞覆盖缺口。

通过条件：同一输入重复运行得到相同 checksum 和相同分层结果。

### Block 1：补齐源表记录和关系判断过程，不生成内部转换

新增或调整：

- 在验证流程中读取并整理 `strategy_fm_dim_order_saleable`；
- 生成每日 BOM 图、SPU 成员和换算依据快照；
- 新增 `shadow_relation_decision`；
- 新增 `shadow_leaf_path`；
- 新增 `shadow_relation_unresolved`；
- 正式输出新增 SPU 层，不再依赖临时脚本聚合。

本块只计算“如果按公司规则应该怎么走”，不改变账本。

测试：

- 每个验收父品日只能有一个根决策；
- `is_orderable` 与 `is_saleable` 不得混用；
- 同一输入的规则快照必须可复现；
- 环、双向边、缺比例、缺商品维度必须不计入正式计算，不能静默留主品或随意拆分；
- 按天×门店/大中小/SPU 输出理论数量影响。

### Block 2：实现公司 BOM 决策树

建议新增：

- `fmetl/relations/company_bom_policy.py`；
- `fmetl/relations/spu.py`；
- 对 `relations/resolver.py` 只保留依据冲突解析，不再承担完整业务决策。

实现：

- 猪/牛/羊有 BOM 强制拆分；
- 非猪牛羊按子品可售数量和主品可售状态分支；
- SPU 目标按可售数量、转换比例和 SKU 编码确定；
- `bom_type/split_mode/sp_level` 写入决策 trace；
- 物料码和名称规则只产生候选，不产生正式库存流。

本块仍只输出 shadow plan，不改库存。

测试：公司材料中的边猪、咸香鸡只/半只、0/1/N 可售分支全部建立固定测试夹具。

### Block 3：递归到叶子

建议新增 `fmetl/facts/multilevel_plan.py`：

- 从每个实际验收商品开始；
- 按 Block 2 决策逐层展开；
- 同一运行快照内做拓扑排序；
- 输出每层中间腿，但外部进货只记一次；
- 到动态叶子停止；
- 环、重复目标、双向 SPU 冲突整组件不计入正式计算。

测试：

- 当前每天 3 个活跃中间节点、8 个二级子节点必须产生完整路径；
- 每个根验收事件只能进入一个关系计划；
- 中间节点流入数量不得被重复当作外部进货；
- 每条路径均有明确叶子或明确未计入正式计算的原因。

### Block 4：数量本地试算计入每日库存和成本

把 Block 3 的计划接入现有统一 DAG，但先只验证数量：

- 来源转出不得超过“期初 + 当日外部进货 + 已完成上游内部流入”；
- 根验收数量必须只入账一次；
- 关系组按各自单位记录，同时保留公共单位平衡字段；
- 不允许用未知损耗自动吸收 BOM/SPU 数量不平衡。

每个小块测试后，按日×门店/大中小/SPU 对比：

- 期初库存量；
- 进货量；
- BOM/SPU/PACK/COMPOSE 净流；
- 期末库存量；
- 已知/未知损耗数量；
- 前一天期末库存与当天期初库存的差。

通过条件：v0.13 前一天期末库存与当天期初库存的差仍为 0；所有已确认关系的转出和转入数量按比例一致；新增关系不能增加无法解释的库存平衡差。

### Block 5：金额与加权成本

保留当前按日加权单位成本的计算：

```text
当日出库单位成本
=（期初库存金额 + 外部进货金额 + 已完成内部流入金额）
 /（期初库存数量 + 外部进货数量 + 已完成内部流入数量）
```

每个正式内部事件：

```text
source_out_amt = source_out_qty × source_issue_unit_cost
Σ target_in_amt = Σ source_out_amt
```

多级过程按拓扑顺序逐层传递金额，金额不能在叶子层重新计算第二次。

猪肉数量可以由父品按 BOM 比例拆出；成本分配计算规则须在第 11 节确认。建议优先使用：

1. 实际库存转换明细金额；
2. 共同重量单位下的父品单位成本；
3. v1.5 `spilit_sale_article_amt/sale_recev_rate` 兼容比例。

不建议把“猪肉分类毛利率”写回库存成本。它可作为展示层对比方案，但会破坏库存金额跨日状态。

通过条件：

- 每个内部事件金额平衡差绝对值 ≤ 0.01；
- 次日期初金额精确等于前日期末金额；
- 未知损耗额的变化必须能拆为数量变化和单位成本变化；
- 按门店/大中小/SPU 审查库存额、损耗额、门店毛利额。

### Block 6：盘点资格和主子冲突

保留“系统记录为 0 且满足条件时可以作为正式盘点”的原有规则，不改用
`created_by != '系统'`。

新增审计：

- 当天有期初库存的商品可盘；
- 当天新验收商品只允许叶子盘点；无叶子才盘商品本身；
- 同一 BOM/SPU 组件主子同时有盘点余额时标记冲突；
- 手工和系统盘点分别保留 `created_at/updated_at` 与来源依据；
- 日清商品出现正式盘点时单列检查。

在用户确认冲突优先级前，本块先输出 `shadow_count_conflict`，不自动删除任何有效盘点。

测试：21279829 的系统 0 实盘必须继续进入正式期末库存；构造主子同时盘点案例，必须被检查识别。

### Block 7：加工成品继续落叶子

- 继续以 `compose_di` 实际数量优先；
- 配方只补实际加工缺侧；
- 原料当天可用数量不足时，整次加工不计算；
- finished SKU 进入与验收商品相同的公司决策器；
- 有完整 BOM/SPU 过程则继续到叶子；无过程则留在 finished SKU；
- 跨大分类加工保留来源分类、目标分类和成本 trace。

重点验证熟食、烘焙、猪肉转熟食和水产类菜肴。禁止因为“只有进货无销售”或名称相似就自动
生成加工关系。

### Block 8：同事五类问题进入候选治理层

以下信息可以用于发现候选，不能直接改正式库存：

- 新旧条码替换；
- 商品名称和规格相似；
- 物料码相同；
- SPU 相同；
- 只有进货无销售、只有销售无进货；
- 长期稳定的正/负未知损耗互补关系。

候选需输出置信度、依据、有效日期和建议关系类型，经人工确认后才形成已确认关系。缺转换系数的
件/公斤关系必须补实测规格，不能假设 `1件=1公斤`。

非日清商品用前一天期末库存转为当天期初库存验证，不要求每天进销平衡；应按关系有效期覆盖完整周后再判断。

## 8. 每块统一测试模板

### 8.1 单元测试

- 0/1/N 可售子品；
- 主品可售/不可售组合；
- 猪牛羊强制拆；
- SPU 0/1/N 可售目标；
- 比例相同按最小 SKU；
- 两层 BOM；
- 环和双向关系；
- 加工成品有/无叶子；
- 系统 0 实盘；
- 主子同时盘点。

### 8.2 日级内部不变量

- 外部进货 exactly once；
- 内部事件来源金额等于目标金额；
- 正式来源数量不透支；
- 次日期初 = 前日期末；
- 非日清库存方程数量、金额平衡差为 0；
- 未知损耗不能承担缺关系、缺比例或重复计入每日库存和成本的平衡差。

### 8.3 分层业务验收

每天输出五个工作表或五个层级：门店、大分类、中分类、小分类、SPU。指标至少包括：

- 期初/期末库存数量和金额；
- 外部进货数量和金额；
- BOM/SPU/PACK/加工流入流出数量和金额；
- 销售数量和金额；
- 已知/未知损耗数量和金额；
- 加权单位成本；
- 门店毛利额；
- 关系覆盖率、不计入正式计算数量、叶子到达率。

v1.5 只作参考，不要求完全相等。判断顺序为：内部不变量、公司规则、分层业务合理性、最后才是
与 v1.5 的差异幅度。

## 9. 建议验收检查

| 检查 | 要求 |
|---|---|
| 跨日数量滚动 | 前一期末与次日期初差为 0 |
| 跨日金额滚动 | 前一期末与次日期初差为 0，允许浮点误差 |
| 内部事件金额 | 每事件平衡差绝对值 ≤ 0.01 |
| 关系唯一性 | 每验收事件唯一根决策 |
| 多级路径 | 正式路径到叶子或明确不计入正式计算 |
| 关系环 | 正式账为 0 个 |
| 缺转换比例 | 不正式转换记录 |
| 外部进货重复 | 0 |
| 未解释关系平衡差 | 不得静默并入未知损耗 |
| 分层覆盖 | 门店/大中小/SPU 完整输出 |
| v1.5 对比 | 门店和大中小毛利差异需可解释；不以完全相等为目标 |

## 10. 风险与回滚

- 所有新规则先写 shadow 表，不覆盖现有 v0.13 正式本地试算结果；
- 每个 Block 有独立开关，失败只关闭新增关系计划；
- 原始源数据副本、关系快照和决策 trace 永久保留，可重放；
- 不直接修改 `sync_strategy_fm.sh`，除非确认新增“库存转换明细”源表；
- 不把候选关系自动升级为已确认关系；
- 不在关系逻辑稳定前调整毛利公式；
- 不因追求 v1.5 数值一致而破坏金额、数量或跨日前后总额相等。

## 11. 需要用户确认的业务问题

以下四项会直接改变正式转换记录，实施相应 Block 前必须确认：

1. **唯一子品可售、主品不可售怎么处理？**  
   验证周有 32 个父品日。建议：全部拆给唯一可售子品；如果这不是公司规则，需要给出正确分支。

2. **“库存转换明细”后台报表对应哪张 Hive/StarRocks 表？**  
   如果能加入 `sync_strategy_fm.sh`，它应成为 parent→leaf 实际转换数量的最高优先级事实；如果拿不到，
   v0.13 只能按静态 BOM、当日可售和换算比例重建理论转换。

3. **SPU 的权威关系和“转换比例最小”字段是什么？**  
   是否以 `dim_goods.spu_id` 分组，并使用 `strategy_fm_dim_article_convert` 的
   `parent_rate/sub_rate`；比较的是验收品消耗量、目标产出倍率，还是别的业务字段？

4. **猪牛羊拆分成本计算规则是什么？**
   建议在统一公斤计算规则下，各部位继承父品相同单位成本；还是继续使用 v1.5 的
   `spilit_sale_article_amt/sale_recev_rate` 比例？公司材料目前只明确了数量，没有明确成本。

另需确认盘点冲突策略：同一 BOM/SPU 组件主子同时有合法盘点时，是优先叶子、优先最新人工记录，
还是整组件不计入正式计算等待人工处理。建议在确认前只告警，不自动选边。

## 12. 推荐执行顺序

```text
Block 0 基线
  → Block 1 可售与关系 trace
  → Block 2 公司决策树 shadow
  → Block 3 递归叶子 plan
  → Block 4 数量本地试算计入每日库存和成本
  → Block 5 加权金额
  → Block 6 盘点冲突
  → Block 7 加工落叶子
  → Block 8 候选关系治理
```

在回答第 11 节问题前，可以安全完成 Block 0 和 Block 1；Block 2 可以实现已明确分支并把未确认
分支不计入正式计算，但不能宣称公司多级 BOM 已完整上线。
