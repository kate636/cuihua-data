## 3. BOM 层级结构（2026-04-22 发现）

### 3.1 FM 门店实际走的是"中间层 BOM"，不是根 BOM

- 典型猪肉 BOM 层级：
  - **根 parent**（整猪 / 白条 / 大妈家黑土猪 A 级 …）—— 全门店今天 `receive_qty=0`、`compose_out_qty=0`
  - **中间 parent**（优鲜排骨 / 优鲜黑猪排骨 / 普罗旺斯番茄 …）—— `receive_qty > 0`
  - **叶子 sub**（优鲜一字排 / 优鲜软排骨 / 优鲜排骨头 …）—— 靠 BOM 分摊
- 2026-04-20 实测：BOM 源表 3062 关系中，只有 `7 个 sub` 的 parent 今天有 qty > 0，
  对应 `t_calc_bom_cost` 只有 7 行。

### 3.2 但中间 parent 自己也缺 `cost_price`

- `优鲜排骨`(20003470) 今天 `receive_qty=3.73 kg`，但 `atomic_cost_price.cost_price=NULL`、
  `atomic_scm` 没记录。
- `优鲜黑猪排骨`(20110673) 同上。
- `普罗旺斯番茄`(20816957) 有 `atomic_scm.outstock_cost_price=10.5` 但 `atomic_cost_price=0`。
- **结果**：`t_calc_bom_cost.bom_unit_cost` 全部 = 0，BOM 分摊**目前没有真正生效**。
- 下一步要做的事（超出 v3.1 范围，待 v3.2 再做）：
  1. **BOM 递归**：中间 parent 的 cost 由更上层 BOM 推导。
  2. **`atomic_scm.outstock_cost_price` 兜底**：供应链出库成本作为 cost_price 的第二层 fallback。
  3. **门店收货金额回填**：确认 `atomic_inventory` 是否真的没有 `receive_amt` 字段，如果有，
     直接用 `receive_amt / receive_qty` 作为 parent 单位成本的兜底。

### 3.3 `atomic_inventory` 没有 `receive_amt`

- 只有 `init_stock_qty / end_stock_qty / receive_qty / day_clear / article_id` 5 个数值维度字段。
- 这意味着门店收货的金额在原子层就是缺失的 —— 必须通过 `cost_price × receive_qty` 事后回填。

## 4. BomRelationExtractor 的 schema 陷阱（2026-04-22 发现）

### 4.1 API 返回列是**字母序**，不是 SELECT 顺序

- QDM BI API 把 `SELECT a, b, c` 的结果按列名字母序返回 DataFrame。
- `DuckDBStore.load_df` 的 `INSERT INTO table SELECT * FROM df` 按**位置**匹配列。
- 如果表是别的流程预建的（比如之前降级空表时手写 schema），列顺序就会错位：
  曾出现 `Could not convert string 'A3XV' to INT32 when casting from source column store_id`。
- **修复方案**：BomRelationExtractor 在每次 `extract()` 开头无条件 `DROP TABLE IF EXISTS
  atomic_bom_relation`，让 `load_df` 按 df 原始 schema 重建，避免历史 schema 残留。
- BOM 是按日全量快照，每日 DROP + REBUILD 无数据损失。

### 4.2 一般教训

- **凡是带 fallback / 降级分支的 extractor**，最好在真正 load 前先 DROP 旧表，避免
  "降级版 schema ≠ 正常版 schema" 导致的列错位。

## 7. BOM 成本分摊 v3.1.1 修复（2026-04-23）

### 7.1 v3.1.0 的三个漏洞

- parent 成本源用 `t_atomic_wide.compose_out_qty × t_calc_avg_price.avg_purchase_price`，
  但散称生鲜的 `avg_purchase_price = 0`（因为 atomic_inventory 缺 receive_amt 字段），
  所以 parent 成本恒为 0，分摊下去也是 0。
- 只做**一级 BOM 分摊**。猪肉实际结构是 3 级（整猪 → 排骨 → 一字排），
  中间层 parent 自己也缺 cost_price，一级分摊跨不过去。
- `profit.py` 的 `is_bom_only_sub` 触发条件是 `day_clear = '0'`（日清），
  但猪肉是非日清（day_clear='1'），永远走库存方程分支，BOM 成本没进 `profit_amt`。

### 7.2 v3.1.1 修复要点

1. **parent 成本主口径切到 `atomic_scm`**：
   `SUM(original_outstock_qty × outstock_cost_price)` 才是供应链给门店的实际成本。
   兜底用原来的 `t_calc_avg_price`。
2. **BOM 递归扁平**：`WITH RECURSIVE` 展开 root→descendant，累乘 dressing_rate，
   限制 depth ≤ 5，用 POSITION 防环。所有 descendant（含中间层）都能分摊到成本。
3. **`is_bom_only_sub` 判据改为 `cost_source = 'BOM'`**：
   只要 effective_unit_cost 来自 BOM，`profit_amt = sale_amt - sale_qty × bom_unit_cost`，
   不再依赖 compose/receive/stock 这些对 BOM sub 永远为 0 的字段。

### 7.3 修复前后的猪肉类门店毛利率

| 阶段 | full_link_rate | store_rate | 与基准 0.2562 的偏差 |
| --- | --- | --- | --- |
| v3.1.0 | 1.0078 | 1.0000 | +74.4 pp |
| v3.1.1 | 0.6523 | 0.6445 | +38.8 pp ✓ 大幅改善 |

### 7.4 仍然偏高的成因（不在 BOM 框架可解范围）

- **黑猪 SKU 当天无 scm 出库**（2026-04-20 只进白猪），所以黑猪 50 个 SKU 仍 `cost_source=MISSING`。
  - 白猪（BOM 命中）：销售 1602 元，门店毛利率 41.8% ← 已修复
  - 黑猪（MISSING）：销售 1020 元，门店毛利率 100%   ← 当天无进货数据
- **预制菜 93.6% 销售额 MISSING**：门店自制（肉+菜二次加工），
  不在当前 atomic_bom_relation（只含一对多分割BOM）的覆盖范围。

### 7.5 下一步改进方向（v3.2 规划）

- 跨天累积 BOM 单位成本：维护滚动 7/30 天的 `bom_unit_cost` 字典，解决黑猪这类当天无进货但有销售的 SKU。
- 接入 `strategy_fm_compose_order_di` 的加工入 BOM（原料 → 成品），覆盖预制菜/熟食。
- 把 `cost_source = MISSING` 的 SKU 打入 DQ 告警，驱动上游补数据。

## 8. 黑猪进货额深挖 + v3.1.2/v3.1.3 修复（2026-04-23）

### 8.1 强现象: 基准表黑猪有 inbound_amount，我们 ETL 没有

在 `strategy_fm_levels_result` 的 "黑白猪" 聚合级别：

| category_name | sale | **inbound_qty** | **inbound_amount** | outbound_cost |
| --- | --- | --- | --- | --- |
| 白猪 | 1676.18 | 92.05 kg | 1548.05 | 1470.96 |
| **黑猪** | 919.45 | **19.50 kg** | **417.50** | 0.00 ⚠️ |

基准表里**黑猪确实有进货 417.50 元**，但 ETL 的 `atomic_scm` 里黑猪根 parent 今天出库 = 0。
意味着 "黑猪进货额" 来源于 **另一张表**，不是 scm。

### 8.2 找到真正的源头: strategy_fm_purchase_di

`strategy_fm_purchase_di` 不是简单的 "进货验收" 表，而是**官方预分摊 BOM 表**：

| 字段 | 含义 |
| --- | --- |
| sale_article_id / sale_article_name | 销售 sku（如 `20110932 优鲜黑猪梅头肉`） |
| article_id / article_name | 销售 sku 的**根 parent**（如 `20045463 优鲜黑猪A级`） |
| sale_article_qty | 当天该 sub 卖出 kg |
| **sale_article_purchase_amt** | **当天 sub 分摊到的进货额**（= sub_qty × 根 parent 均价 × 部位加价率） |
| **avg_inbound_price** | **根 parent 的滚动均价**（解决跨日库存时间错配） |

黑猪 8 个 SKU 在这张表里 `sale_article_purchase_amt` 合计 215.21 元，
`avg_inbound_price` 统一 **21.41 元/kg**。

### 8.3 v3.1.0 的致命漏洞

原版 `inventory_extractor.py` 只从这张表拿了 3 列：
`sale_article_qty` / `init_stock_qty` / `end_stock_qty`。
**官方预分摊的成本字段 `sale_article_purchase_amt` + `avg_inbound_price` 被完全丢弃。**

下游 `avg_price.py` 用 `cost_price` 套算加权均价，但散称生鲜的 `cost_price=0`，
所以 `avg_purchase_price=0`，成本口径彻底断裂。

### 8.4 v3.1.2 / v3.1.3 修复

1. `inventory_extractor.py`: 把 `sale_article_purchase_amt` / `avg_inbound_price` /
   `init_stock_amt` / `end_stock_amt` 全部拉回。
2. `merge.py`: 在 `t_atomic_wide` 新增 `receive_amt_src` / `avg_inbound_price` /
   `init_stock_amt_src` / `end_stock_amt_src`。
3. `avg_price.py`: `avg_purchase_price = COALESCE(cost_price, avg_inbound_price, 0)`。
4. `amounts.py`:
   - `receive_amt / init_stock_amt / end_stock_amt` 优先用官方预分摊，
     回退 `qty × avg_price`。
   - `cost_source` 加第 3 层 `PURCHASE_AVG`：
     `DIRECT (cost_price) → BOM (递归自造) → PURCHASE_AVG (avg_inbound_price) → MISSING`。
5. `profit.py`: `is_bom_only_sub` 扩展为 `cost_source IN ('BOM','PURCHASE_AVG')`，
   这类 sub 都走销售方程 `profit = sale_amt - sale_qty × effective_unit_cost`。

### 8.6 剩余 ~20pp 差距的成因

对于 PURCHASE_AVG 分支，我们用 `sale_qty × avg_inbound_price` 一刀切，但实际上
`avg_inbound_price` 是**整头猪的均价**（21.41 元/kg），散称卖的梅头肉应该有
更高的部位加价率（cost_rate）。基准表可能用了更细的 SKU 级成本表（`strategy_fm_inventory_pool_di`
244k 行库存成本价池？）—— 留给 v3.2 排查。

## 9. v4.0.0 重构落地（2026-04-23）

### 9.1 重构动机

v3.1.3 虽然把猪肉毛利率从 100% 压到 46.44%，但仍然 vs 基准 25.62% 差约 20pp：
原因是 `purchase_di` **95.5% 的行并不是 BOM 分摊行**，它本质是父级进货汇总表，
不具备 parent×sub 双维度 qty/金额。

2026-04-23 探表发现真正的 BOM 分摊事实表是 `strategy_fm_receive_sale_di`：

- 21 列字段完整覆盖 parent×sub 两维；
- `sale_article_qty` / `spilit_sale_article_amt` 就是"当天 sub 从本 parent 拆出的 kg / 元"；
- `rate` / `sale_recev_rate` 是归一化比例，直接可用作 cost_rate；
- 天然解决了 v3.1.x 需要自造递归 BOM 的核心复杂度。

因此决定重构为 v4.0：**以 `strategy_fm_receive_sale_di` 为 BOM 拆分事实主源**，
把 calculated 层拆成四张职责明确的表，并新增两张 AI 溯源表。

### 9.2 v4.0 四张 calculated 表分工

| 表 | 粒度 | 职责 |
|---|---|---|
| `t_calc_bom_alloc` | store × day × parent × sub | BOM 分摊事实（receive_sale 优先，compose fallback，bom_rel 兜底）+ cost_rate 反推 |
| `t_calc_sku_cost` | store × day × sku | `effective_unit_cost` 四级 fallback（DIRECT / BOM_ALLOC / PURCHASE_AVG / MISSING）+ `cost_source` tag |
| `t_calc_stock` | store × day × sku | 库存 + 未知损耗三支（day_clear / know_lost>0 / 普通）+ 官方 end_stock 对比 |
| `t_calc_profit` | store × day × sku | 销售方程 `store_profit_sales` + 库存方程 `store_profit_stock` 双落盘，供应链 / 全链路毛利 |

### 9.3 新增两张 AI 溯源底表

- `t_fm_bom_breakdown`：每 sub × parent 一行，暴露 `parent_unit_price` /
  `dressing_rate` / `cost_rate_effective` / `sub_alloc_amt` / `sub_qty_source` /
  `cost_rate_source`。AI 对"SKU-X 毛利为什么是 Y"问题可直接追到 parent 级分摊。
- `t_fm_stock_roll`：每 sku 展开 8 个库存分量（init / receive / compose_in /
  compose_out / sale / know_lost / unknow_lost / end），同时落 qty 和 amt 两份。
  AI 可直接回答"为什么今天期末是 X"。

### 9.4 门店毛利双口径（C2-a+b）

v4 同时落盘两条口径，方便校验差异：

```
store_profit_sales = sale_amt - sale_qty × effective_unit_cost
                   - know_lost_amt - unknow_lost_amt

store_profit_stock = sale_amt
                   - (receive_amt + compose_in_amt - compose_out_amt)
                   + (end_stock_amt - init_stock_amt)
                   - know_lost_amt - unknow_lost_amt

store_profit_diff  = store_profit_sales - store_profit_stock
```

差异大的 SKU → 库存方程有漏数据（init / end / loss 口径不齐），可直接定位问题。

### 9.5 未知损耗假设（B1-a + B2-a+b+c）

- 日清商品（`day_clear='0'`；`'1'`=非日清、`'2'`=合计）：`end_stock=0`，`unknow_lost` 由库存方程兜底得出；
- 有盘点动作（`know_lost_amt > 0`）：`unknow_lost=0`，公式推 end；
- 普通非日清：`unknow_lost=0`（B1-a 假设），公式推 end。

### 9.6 进货量根 parent 口径（D2-c）

`receive_sale_di.inbound_qty` 优先，fallback `scm_di.original_outstock_qty`，
再 fallback `purchase_di.receive_qty`。v3.1 只看后两者。

### 9.7 日初口径（D1-b）

`init_stock_amt` 每天取官方 `purchase_di`（不做自算接力）；
自算 end 仅作为 `end_stock_amt_diff` 校验字段。这样日日独立可重跑。

### 9.8 三段对标脚本

`python -m fm_etl_v3.scripts.verify_v4` 输出：

1. **SKU 级 vs `allowance_di.profit_amt`**：top20 差异 SKU；
2. **大类级 vs `strategy_fm_levels_result`**：毛利率偏差；
3. **库存自算 vs 官方**：`end_stock_amt_diff` top20。

### 9.9 v4 新表速查

冒烟测试用 `SELECT * FROM t_fm_bom_breakdown WHERE sub_article_id='20110932'`
就能看到优鲜黑猪梅头肉今天从多少个 parent 拆出来、每个 parent 分了多少额、
走的是 RECEIVE_SALE / COMPOSE / BOM_THEORETICAL 哪条路径。

### 9.10 已知风险

- `receive_sale_di` 若某天上游缺失 → pipeline 自动降级到 `bom_rel × purchase.receive_qty` 理论值；
- `order_receive_di` / `dim_article_convert` 暂空，v4 不依赖，骨架已预留；
- `allowance_di.profit_amt` **仅做校验基准**，不参与毛利计算。
