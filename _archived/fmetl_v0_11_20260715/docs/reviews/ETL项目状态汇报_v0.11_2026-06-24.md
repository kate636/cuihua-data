## 一、我们在做什么、为什么

### 1.1 在做什么

围绕 **fmetl v0.11**（翠花 FM 新 ETL）推进三件事：

1. **对齐 QDM 旧 ETL**：大分类毛利大致一致，SKU 级允许差异。
2. **全链路审计**：BOM、物料号、库存、加工逻辑与文档一致性（见 [REVIEW-008](REVIEW-008-full-chain-logic-audit.md)）。
3. **可汇报的状态说明**：差异来源、已知 bug vs 口径差、后续改进路径。

### 1.2 为什么要做

| 问题 | QDM 旧链路 | fmetl 目标 |
|------|-----------|-----------|
| BOM | 分摊不准、难溯源 | 共享组 + 单位归一化 + 父品转移 |
| 重刷 | 依赖 Hive 全链路 | 按日期范围本地重跑 |
| 日清/加工 | 硬编码或源表被动 | API 可配置 + Web 管理配方 |
| 数据基建 | 双重收货、负库存利润泄漏等 | 逐项修复（FIX-017/019/020 等） |

**核心定位**：不是「每个 SKU 和 QDM 完全一样」，而是 **销售/进货可信 + 大分类毛利合理 + BOM/加工可维护、可审计**。BOM 相关 SKU 级差异是**预期口径差**，不是阻塞项。

## 五、差异原因分层解释

### 5.1 完全没有差异（把握 95%+）

销售额、进货额与 QDM **同源**。差异 100% 来自成本/库存/损耗计算层（[REVIEW-007](REVIEW-007-clamp-cost-leak.md) 全口径分解）。

### 5.2 大分类为何有时仍差 10%～40%

| 原因 | 说明 | 可否修 |
|------|------|--------|
| BOM 成本归集 | FM 共享组+单位归一化 vs QDM 旧算法 | 部分口径差 |
| EUC 算法 | FM 加权平均含期初 vs QDM cost_price | 结构性 |
| 负库存/日清 | FIX-019/020 已修利润侧 | 利润已对齐 |
| 日清覆盖 | FM 猪肉/熟食/烘焙 API 覆盖 vs QDM 不覆盖 | 业务选择 |
| 加工关系 | FM 22 条烘焙配方，熟食几乎无 | 可补数据 |
| 零成本 SKU | 136 行有销售无 EUC | FIX-002/011 待做 |

### 5.3 SKU 级为何可以不一致

1. BOM 父/子利润转移，记账粒度不同，**品类合计才是验收单位**。
2. FM 有 day_clear 0/1/2 三值，QDM SKU 仅 dc='1'。
3. 同 matnr 多规格尚未合并（A进B出表空骨架，未做）。

## 六、FM ETL 相对 QDM 的逻辑差异

| 维度 | QDM 旧 ETL | fmetl v0.11 |
|------|-----------|-------------|
| 成本 | 源表 cost_price | 加权 EUC（期初+进货+BOM+加工） |
| 毛利 | 不含完整 BOM 四流 | 含 bom_in/out + compose + FIX-019/020 透支扣减 |
| 负库存 | 允许负期末 | end 钉 0，unknow 记盘盈，利润扣 neg_clamp_cost_amt |
| 损耗 | 源表 know/unknow | 库存方程残差（可为负=盘盈） |
| 日清 | dim 静态 | 猪肉/熟食/烘焙 API 动态 |
| BOM | 历史多版 | 共享组 + qty/qty_sub 双单位 + 父品转移 |
| 加工 | 源表 compose | 配方推算 + 价值守恒 |

## 七、相对 QDM 的优化（项目核心价值）

1. **BOM 分摊可溯源**：`t_fm_bom_breakdown`（parent×sub 明细）
2. **共享组 + 单位归一化**：修复「1 箱 vs 10kg」类错配
3. **父品残余库存转移**：父品 end→0，成本按比例转子品
4. **日清可运营配置**：日清标签 API + 前端管理
5. **加工关系 Web 管理**：`:5003` + `processing-relation.html`，ETL 自动读配方
6. **跨日重刷**：按日期范围重跑，不依赖 Hive 全链路
7. **数据基建修复**：双重收货（FIX-017）、负库存利润泄漏（FIX-019/020）
8. **matnr 交叉验证**：FIX-018 异常 EUC 告警
9. **库存八要素滚动**：`t_fm_stock_roll` + balance 校验
